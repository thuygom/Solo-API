# 적용 사례

2026년 10월부터 11월까지, B2B SaaS 한 곳(모바일 앱과 AI 비서)에서 이 방식을 썼다.
AI 서비스 여러 개가 앱의 업무 DB(PostgreSQL)를 쓰고, 앱 서버와 DB 스키마는 시스템 백엔드 팀이 소유한다.
제품, 회사, 내부 시스템의 이름은 뺐고, 내부 구조를 드러내는 개수는 비율이나 근사치로 바꿨다.
수치는 적은 시기의 관측값이고, 부하 시험이나 운영 SLO가 아니다.

## 출발점

AI 서비스는 맥락을 두 길로 받았다. 하나는 앱 서버가 AI API를 부를 때 요청 본문에 실어 보내는 값, 다른 하나는 앱 서버가 따로 만든 조회 API였다.
AI 쪽에 필드 하나가 필요해질 때마다 앱 서버의 수정과 배포가 따라왔다.

## 읽기 매퍼 (2026년 10월)

- 한 AI 서비스에 고정 SQL 매퍼를 만들고, 같은 빌드를 다른 AI 서비스 세 곳에 설치했다.
- 일반 맥락 조회는 RDB만 보고, 실패해도 예전 조회 API나 다른 저장소로 돌아가지 않게 했다.
- 배포된 서비스에서 운영 계정 표본으로 맥락별 두 번씩, 350건 남짓을 조회했다. 오류는 없었다.

| 조회 | p50 (ms) | p95 (ms) |
|---|---:|---:|
| 텍스트 분석 맥락 | 37 | 50 |
| 일정 분석 맥락 | 29 | 40 |
| 음성 분석 맥락 | 40 | 51 |
| 기존 노트 조회 | 41 | 54 |
| 회사 조회 | 22 | 30 |
| 분석 맥락 동시 2건 | 53 | 59 |

연결, SQL, 복호화, 감사, 정규화 시간을 포함한다. 이 범위에서 조회 지연이 병목이 되지는 않았다.

## 요청 최소화 (2026년 11월)

- 회사 리포트 같은 API의 필수 요청이 계정 ID와 회사 ID 두 개로 줄었다. 회사 정보, 소속 회사, 재무는 매퍼가 읽는다.
- 정해진 시각에 만드는 요약 브리핑은 AI 쪽 스케줄러가 대상 계정을 매퍼로 찾아 만들고 저장한다. 앱 서버는 저장본을 조회해 발송만 한다.
- AI 비서 도구를 열몇 개 만들었고, 원 API가 아직 없는 도구는 보류로 내놓았다. 답장 초안 도구의 입력은 노트 ID와 답장 방향뿐이다.

## 원 시스템이 만들어 주기로 했던 API

앱 서버 팀이 AI 쪽에 제공하기로 했던 API 후보 70여 개를 하나씩 분류했다.

| 판단 | 비율 |
|---|---:|
| 매퍼로 구현 (운영 스키마를 복제한 임시 DB에서 검증) | 약 47% |
| AI 쪽에서 처리 (기존 조회 조합, AI 판단) | 약 7% |
| DB 변경 요청 (테이블, 컬럼, 읽기 권한) | 약 26% |
| API로 유지 | 약 20% |

API로 남은 것의 이유는 [SA-501](../SPEC.md#5-경계)의 다섯 가지 그대로였다. 파일 객체, 링크·토큰 발급, 앱 서버 안의 비동기 작업, 계정 간 전달, 앱 DB에 없는 원장이다.

## 스키마 이전

같은 달에 앱의 새 DB 스키마로 옮겼다. 테이블 수가 1.5배로 늘었고, 공통 테이블 대부분에서 계정 ID의 타입이 바뀌었다.

| 단계 | 결과 |
|---|---|
| 이식 전 | 일반 맥락 읽기 문장의 약 80%가 그대로 동작 |
| 방언 등록부 작성 | 기존 문장을 복사해 바뀐 부분만 덮어씀. 응답 키는 유지 |
| 이식 후 | 호출하지 않는 문장 하나를 빼고 모든 읽기 문장 통과 |

새 스키마에는 기존 DB에서 요청해야 했던 테이블 일부가 이미 있어서, 매퍼로 대체하거나 부분 대체할 수 있는 후보가 절반을 넘었다.

## 배운 것

- 앱 서버의 엔티티 훅이 저장 전에 계산하던 파생 값을 매퍼에 옮겨야 했다 (SA-208).
- 휴지통 기록, 실행 이력, 기능 플래그처럼 앱 코드에만 있는 규칙은 확인 전까지 쓰지 않았다.
- 전용 DB 역할은 도입 초기에 요청해야 한다. 역할이 늦게 나오면 그동안의 경계가 약하다 ([보안 고려 사항](security.md)).
- 관리용 문장은 처음부터 일반 등록부와 떼어 두는 편이 낫다 (SA-104).
