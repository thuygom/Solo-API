# 왜 Solo-API인가

## 문제

AI 서비스가 업무 시스템의 데이터를 얻는 흔한 길은 두 가지다.

1. **요청에 실어 받기.** 원 시스템이 AI API를 부를 때 사용자 정보, 연락처, 그룹을 요청 본문에 넣는다. 맥락이 늘 때마다 원 시스템이 본문을 고친다.
2. **조회 API 받기.** AI가 필요할 때 조회하도록 원 시스템이 조회 전용 API를 만든다. 고정 토큰 하나가 방벽이 되기 쉽고, 필드가 늘 때마다 API가 바뀐다.

두 길 모두 일은 AI 쪽에서 생기는데 비용은 백엔드 팀이 낸다. 기능 하나에 두 팀의 일정이 맞아야 하고, AI 기능이 늘수록 백엔드의 대기열이 길어진다.

## 바꾸는 것

Solo-API는 AI 서비스가 원 시스템의 DB를 직접 읽고 쓰게 한다. 대신 무엇을 읽고 쓸 수 있는지를 코드에 전부 미리 적어 둔다.

- 실행할 수 있는 SQL은 등록부에 있는 것뿐이다. 리뷰어는 등록부 하나를 읽으면 AI 서비스가 DB에 할 수 있는 모든 일을 안다.
- 모델은 SQL을 만들지 않는다. 모델은 도구를 고르고, 사용자만 아는 값을 채운다.
- 대화가 아닌 일(정해진 시각의 브리핑, 화면 자동화)은 작업과 스케줄러로 돈다.

결과적으로 원 시스템에 하는 요청은 세 가지로 줄어든다.

| 남는 요청 | 예 |
|---|---|
| 역할과 권한 | 읽기 전용 역할, 테이블·컬럼 단위 쓰기 역할 |
| 저장할 자리 | 새 테이블, 새 컬럼 |
| API로 남아야 하는 일 | 토큰 발급, 파일 객체, 계정 간 권한 판정, 서버 안의 비동기 작업 |

## 대체할지 판단하는 순서

원 시스템에 요청하려던 API 하나마다 다음을 차례로 묻는다.

1. DB 행을 읽거나 쓰는 것으로 끝나는가? → 매퍼로 한다.
2. 이미 있는 조회를 조합하거나 AI가 판단하면 되는가? → AI 서비스 안에서 한다.
3. 저장할 테이블이나 컬럼이 없는가? → DB 변경을 요청하고, 생기면 매퍼로 한다.
4. [SA-501](../SPEC.md#5-경계)의 다섯 가지에 걸리는가? → API로 남긴다.

## 앱 서버를 거치지 않아서 생기는 차이

매퍼로 쓰면 원 시스템 서버가 하던 일 일부가 일어나지 않는다. 대체 범위를 정할 때 같이 본다.

| 원 시스템 서버가 하던 일 | 매퍼로 쓸 때 | 대응 |
|---|---|---|
| DB 트리거 | 그대로 실행된다 | 쓰기 역할에 트리거가 쓰는 테이블 권한을 준다 |
| 푸시, 화면 갱신 | 생기지 않는다 | 요청 테이블에 쓰고 원 시스템이 발송한다 (SA-207) |
| 서버 감사 로그 | 생기지 않는다 | 매퍼가 자체 감사 기록을 남긴다 (SA-113) |
| 입력 검증 | 다른 값이 들어갈 수 있다 | 상태값 허용 목록을 매퍼에 둔다 |
| 엔티티 훅의 파생 값 | 계산되지 않는다 | 같은 계산을 옮기고 시험으로 맞춘다 (SA-208) |

## 한계

- **경계가 옮겨 간다.** API 계층의 인증 대신 DB 역할, 고정 문장, 네트워크 허용 목록이 경계다. 전용 역할을 받지 못하고 원 시스템의 계정을 같이 쓰면 경계가 고정 문장의 계정 조건과 행 수준 보안만 남는다. 이 상태로 오래 두지 않는다.
- **스키마에 묶인다.** 컬럼이 바뀌면 문장이 깨진다. 스키마 대조와 문장 호환성 검사를 같이 유지해야 한다 (SA-115).
- **원 시스템의 규칙을 모르면 쓰지 못한다.** 서버 코드에만 있는 규칙은 확인 전까지 미지원으로 둔다.
- **같은 언어일 때 가장 싸다.** 매퍼를 라이브러리로 설치할 수 없는 서비스에는 내부 연동이 따로 필요하다.
- **"한 사람"은 요청 단위가 줄어든다는 뜻이다.** DBA와 원 시스템 팀의 일이 없어지지 않는다. [사례](case.md)에서도 매퍼로 끝난 것은 후보의 절반이 안 됐다.
