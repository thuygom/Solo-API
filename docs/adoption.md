# 도입 순서

한 번에 옮기지 않는다. 요청하려던 API 하나, 업무 하나씩 옮긴다.

## 1. 읽기부터

1. 원 시스템 팀에 **읽기 전용 DB 역할**을 요청한다. 필요한 스키마만 SELECT 권한을 받고, 세션 기본값을 읽기 전용으로 둔다.
2. AI 서비스가 원 시스템에서 받아 오던 맥락(요청 본문에 실려 오던 값, 조회 API로 받던 값)을 목록으로 만든다.
3. 맥락마다 문장을 하나씩 등록한다. 계정 조건, 상한, 정렬을 문장에 넣는다.
4. 소비하는 서비스에 매퍼를 설치하고, 요청 본문의 해당 필드는 무시해도 되게 바꾼다. 원 시스템이 그 필드를 보내는 것은 그대로 둔다.
5. 실제 조회 지연을 잰다. 연결·실행·복호화·감사 시간을 포함하고, 표본 수와 날짜를 적는다.

## 2. 쓰기

1. 쓰기 역할을 요청한다. 테이블·컬럼 단위로 필요한 것만 받는다. 트리거가 쓰는 테이블 권한도 함께 받는다.
2. 원 시스템 서버가 저장 전에 계산하던 값(파생 컬럼, 상태 규칙)을 서버 코드나 담당자에게 확인한다. 확인하지 못한 연산은 미지원으로 둔다.
3. 운영 스키마를 복제한 임시 DB에서 쓰기 시험을 돌린다. 운영 DB에서 시험하지 않는다.
4. 알림처럼 원 시스템이 발송해야 하는 일은 요청 테이블을 제안한다.

## 3. 도구

1. 사용자가 대화에서 시킬 일만 도구로 만든다. 스케줄러나 시스템이 부르는 일은 도구 목록에 넣지 않는다.
2. 도구마다 아래 작업표를 채운다.
3. 가짜 원 시스템을 상대로 계약 시험을 쓴다. 정상, 거절, 충돌, 중복, 중단을 확인한다.

| 항목 | 정리할 내용 |
|---|---|
| 업무와 사용자 | 누가 어떤 결과를 원하는가? 성공은 어디서 확인하는가? |
| 기존 경로 | 지금 쓰는 화면, API, 배치, RPA와 시험 환경 |
| 주체와 범위 | 누구로 실행하며 어느 조직·계정·자료에 접근하는가? |
| 효과 | read, generate, write 중 무엇인가? |
| 입력 | 서버가 읽을 수 있는 값과 사용자만 아는 값(Question)을 나눈다 |
| 확인과 승인 | 실행 전에 무엇을 보여 주고, 누가 승인하는가? |
| 오류와 복구 | 결과를 모를 때 어떻게 확인하고 누가 복구하는가? |
| 운영 조건 | 개인정보 보관, 처리 시간, 비용, 동시 실행 제한 |

## 4. 작업과 스케줄러

1. 정해진 시각에 도는 일은 업무 키에 날짜를 넣는다.
2. 생성 경로는 루프백 같은 내부 경로에서만 연다. 소비자에게는 저장본 조회만 내놓는다.
3. 화면만 있는 시스템은 미리보기·접수·상태 조회 세 도구로 나누고, 업무 키로 원 시스템을 다시 조회하는 방법을 먼저 정한다. 그 방법이 없으면 RPA로 쓰기를 시작하지 않는다.

## DB 변경 요청서

요청서의 단위는 API가 아니라 테이블과 컬럼이다.

| 항목 | 예 |
|---|---|
| 대상 | 테이블 또는 컬럼 이름, 타입, 기본값, NULL 허용 |
| 필요한 기능 | 이 자리가 있어야 동작하는 기능 한 줄 |
| 기존 구조 대조 | 같은 역할의 테이블·컬럼이 이미 있는지 확인한 결과 |
| 원 시스템이 할 일 | 있으면 한 가지만 (예: 요청 테이블의 대기 행을 기존 발송 경로로 넘긴다) |
| 권한 | AI 쓰기 역할에 줄 권한 |
| DDL | 바로 적용할 수 있는 문장 |

## 구현을 AI에게 맡길 때

```
목표와 사용자: [업무, 사용자, 성공 기준]
자료: [기존 저장소, 스키마, API·RPA 문서, 시험 환경, 담당자]
호환성: [클라이언트, MCP·SDK 버전, stdio/HTTP, 인증]
권한: [주체 검증, 원 시스템 위임, 데이터 범위, 사람만 하는 일]
도구 후보: [업무 의도, 입력·출력, 효과, 복구, 승인]
제약: [개인정보, 로그, 속도·동시성, 운영 조건]
수행: 자료를 읽고 사실·가정·미결을 나눈다. SPEC.md의 규칙 번호를 붙여 도구별 계약을 먼저 제안한다.
허용된 시험 데이터로 검증하고, 시험하지 못한 범위를 보고한다. 없는 API나 권한을 있다고 가정하지 않는다.
```
